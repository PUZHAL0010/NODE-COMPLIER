2. Executive Summary

The Distributed Node.js Web IDE & Secure Code Execution Platform is an enterprise-grade, browser-based development environment engineered to provide an instant, frictionless, and secure coding experience for full-stack JavaScript, TypeScript, and Node.js applications.

Unlike simplistic "toy compilers" that run basic scripts using unsandboxed local processes, this platform implements a distributed microservice architecture featuring an asynchronous task queue (BullMQ on Redis 7), isolated sandbox runtimes (both Linux cgroup-hardened containers and local process sandboxes), an in-memory TypeScript compiler, real-time Server-Sent Events (SSE) stream multiplexing, and an isolated multi-page HTML/CSS/JS preview engine.

The platform guarantees deterministic execution, hard resource caps (512MB RAM, 1.0 CPU, 32 PIDs, 5000ms timeout), path traversal protection, zero secret leakage, and browser state persistence across sessions.

3. Problem Statement

Local development environments present steep barriers for modern software teams, coding interviews, and education:

  • Environment Mismatches & "Works on My Machine" Syndrome: Varied OS versions, local Node versions, and global binaries create reproducibility issues.
  • Dangerous Untrusted Code Execution: Running arbitrary student, interview, or user submissions locally exposes host filesystems, environment tokens, and network sockets to malicious scripts.
  • Heavy Machine Footprint: Setting up Docker, Redis, and full IDE suites on lightweight devices is cumbersome.
  • Multi-User Scaling Bottlenecks: Naive execution backends suffer race conditions, CPU exhaustion from infinite loops, and memory starvation under concurrent traffic.

4. Existing Systems

Current solutions generally fall into two categories: basic online editors that only execute single files with unrestricted local eval()/child_process (dangerous, lacking multi-file support), or heavyweight Cloud IDEs (e.g. Gitpod, Codespaces) that take 45–90 seconds to provision a full virtual machine.

6. Proposed System

The proposed platform bridges the gap between instant responsiveness and enterprise-grade security isolation. It features a side-by-side Monaco editor workspace with persistent tab management, high-contrast dark theme, instant Ctrl+Enter execution, sub-30ms execution latency, and a distributed BullMQ/Redis worker cluster supporting 150+ concurrent developers.

7. Measurable Objectives

  1. Execute standard Node.js 20 LTS programs with P50 latency < 20 ms.
  2. Support multi-file projects with cross-file relative imports (./utils.js, config.json).
  3. Transpile TypeScript source in-memory and return structured Monaco diagnostic markers.
  4. Enforce a hard 5000ms timeout and reclaim 100% of child processes.
  5. Bound stdout/stderr to 1 MB to eliminate memory exhaustion DoS vectors.
  6. Persist all user-created files and tabs in browser storage across page reloads.

8. Key Features Breakdown

  • Frontend IDE: Monaco Editor, multi-tab switcher, file drawer, real-time output terminal, duration badge (⚡ 15 ms ✔), and I/O stdin console.
  • Backend Gateway: Stateless Express API, Zod schema validation, sliding-window rate limiting (10 req/min), SSE stream broker.
  • Execution Runtimes: Dual-mode runtime abstraction (ProcessSandboxRuntime for rapid local dev; DockerSandboxRuntime for locked-down production).
  • Multi-Page Preview: Virtual Client Router intercepting relative .html anchor links inside a CSP-sandboxed iframe.

14. End-to-End Execution Workflow

When a developer writes code and clicks Run (or presses Ctrl+Enter):

  1. Client Ingress: Monaco collects all project files and submits an ExecutionRequest JSON payload to POST /api/v1/jobs.
  2. Validation & Rate Guard: Gateway validates paths via validateProjectFiles() and checks IP quotas.
  3. Job Dispatch: Enqueued into BullMQ or dispatched immediately in standalone development mode.
  4. Compilation & Linking: If TypeScript files exist, tsCompiler compiles them to ES2022. Workspace links host node_modules.
  5. Sandbox Execution: Runtime spawns Node with memory bounds (--max-old-space-size=512) and sets a 5000ms timeout guard.
  6. Real-Time Streaming: Stdout chunks pass through BoundedOutputCollector and stream live to the browser console via SSE.
  7. Cleanup & Completion: Ephemeral workspace is unlinked and deleted; duration badge updates (⚡ 18 ms ✔).

25. Security Architecture & Threat Model

The platform enforces multi-layered defense-in-depth:

  • Path Traversal Defense: normalizeAndValidatePath() rejects ../, ..\, null bytes, absolute paths, and Windows device names before reaching the filesystem.
  • Buffer Exhaustion Defense: BoundedOutputCollector clamps stdout/stderr to 1 MB, eliminating memory denial-of-service vectors.
  • Environment Secret Scrubbing: Sandboxed processes receive only sanitized variables (NODE_ENV, NODE_PATH, PATH, HOME, TMPDIR), preventing host credential leakage.
  • Docker Sandbox Hardening: --network none, --cap-drop ALL, --read-only root filesystem, --memory 512m, and --pids-limit 32.

39. Judge Live Demonstration Workflow (5-Minute Script)

  1. Step 1 (Hello World & Speed): Open http://localhost:3000, write console.log("Hello, World!");, press Ctrl+Enter. Show the instant green duration badge (⚡ 18 ms ✔).
  2. Step 2 (Multi-File Module Import): Click + to add utils.js, export an add(a, b) function, import it into index.js. Run and show seamless cross-file execution.
  3. Step 3 (Full Express & API Server): Write an Express app with in-memory routes (e.g. Student Management), perform a self-test fetch() request, and print structured JSON output.
  4. Step 4 (Infinite Loop & Sandbox Guard): Write while(true){} and click Run. Demonstrate that after exactly 5000ms, the sandbox kills the loop cleanly without freezing the browser or crashing the server.
  5. Step 5 (Multi-Page HTML Preview): Click Preview tab, navigate between index.html and about.html via virtual router inside the CSP-isolated iframe.
